# Clinical records (R01/R02)

Clinical records owns appointment-scoped notes, prescriptions and their items.
The service provides PostgreSQL storage, appointment-scoped note and draft
prescription APIs, and durable read auditing. Transactional issuance/events
follow in R03. API shapes are defined by `contracts/prescription-order-quote.md`.

From the repository root, install the service into its own virtual environment
(its `app` package name is shared with other independently deployed services):

```powershell
python -m venv services/clinical_records/.venv
services/clinical_records/.venv/Scripts/python -m pip install -r services/clinical_records/requirements.lock.txt
services/clinical_records/.venv/Scripts/python -m pip install --no-deps -e packages/python_common -e services/clinical_records
```

Create a dedicated service role and schema as a database administrator using
`scripts/create-local-schema.sql` (synthetic local credentials only; change the
database grant if not using `telelink`). The service role owns its own schema and
must not own or have access to another service's schema. The migration does not
create roles, change shared schemas or grant itself privileges.

Then run from `services/clinical_records`:

```powershell
$env:SERVICE_DATABASE_URL='postgresql+psycopg://clinical_records:local-demo-only@localhost:55432/telelink'
.venv/Scripts/python -m alembic upgrade head
.venv/Scripts/python -m alembic check
```

The `clinical_records.alembic_version` table is service-local. Upgrade is safe to
repeat. `alembic downgrade base` deletes clinical-record tables and data; use it
only on a disposable database. It leaves the role/schema/version table intact.

`notes` stores one note per appointment. `prescriptions` allows one non-voided
prescription per appointment, with draft/issued/voided state and issue timestamp
checks. Items reference only their local prescription, retain the display-name
snapshot and require positive dispensing quantities and nonblank instructions.
No price or trusted total is stored in a prescription. UUIDs are generated by the
application, timestamps use UTC, and database triggers preserve creation time and
refresh update time for both ORM and SQL writes.

The API validates appointment context against scheduling and current membership
against identity on each request. Only the assigned active doctor can write, and
only during `in_progress`. The owning patient and assigned active doctor can read;
clinic/platform administrative roles confer no clinical access. All four stored
context IDs must match scheduling. Reads are committed to `read_audits` before
returning content; a failed audit returns 503. Audits contain actor/resource/context
IDs, request ID and time, never clinical text or credentials. Empty list requests
are also audited. Ordinary request logs exclude payloads and query strings.

Prescription items are validated against the owning clinic's active fulfilment
catalogue using the doctor's access token; names and context come from the server.
Item replacement is atomic, with parent-row locking. Appointment advisory locks
serialize first note/prescription creation. Issued and voided content is immutable
through these public routes. Signed 15-minute cursors bind list position to the
current subject, permissions and appointment filter. List reads recheck scheduling
and audit each returned prescription. Responses use `Cache-Control: no-store`.

## Run the API

Copy `.env.example` to `.env` in this service directory and replace the Floci pool
and client IDs with the bootstrap values. Configure the identity, scheduling and
fulfilment base URLs; include their ingress API prefix when accessing them through
a proxy. Use independent random cursor secrets and HTTPS outside local/test.
No shared Compose or frontend routing changes are included in R02.

After migrating to revision `0002`, run from this directory:

```powershell
.venv/Scripts/python -m app
```

The API listens on port 8005 by default. `/health/live` checks process health;
`/health/ready` checks required configuration and migration revision (it does not
probe upstream health). Swagger is at `/docs` locally. Routes already contain the
`/api/v1/clinical-records` prefix; keep `SERVICE_ROOT_PATH` empty for direct local
access. A same-origin reverse proxy can forward these paths in a later integration.

Implemented C04 routes:

- PUT/GET `/api/v1/clinical-records/appointments/{appointment_id}/note`
- POST `/api/v1/clinical-records/appointments/{appointment_id}/prescriptions`
- PATCH/GET `/api/v1/clinical-records/prescriptions/{prescription_id}`
- GET `/api/v1/clinical-records/prescriptions` (`appointment_id`, `limit`, `cursor`)

POST issuance is reserved for R03: it must commit the issued state and outbox event
together, with idempotent retries. R02 does not expose an issuance transition that
could lose its event. Service-only dispensing/document projections and frontend
connection remain follow-up integration work. No changes to shared contracts.

For verification, prepare a **disposable** PostgreSQL database with the above
role/schema plus `tests/isolation-fixture.sql` as an administrator. The latter
creates an unrelated read-only sentinel to verify migration isolation and role
restrictions. Tests require explicit opt-in because they downgrade the schema:

```powershell
$env:TEST_DATABASE_URL=$env:SERVICE_DATABASE_URL
$env:CLINICAL_RECORDS_TEST_ALLOW_RESET='1'
.venv/Scripts/python -m pytest -q
.venv/Scripts/python -m ruff check .
.venv/Scripts/python -m ruff format --check .
```

Verification evidence and remaining integration limits: [docs/api.md](docs/api.md).
