# Tenant service (A07-A10)

Tenant owns clinic data in the `tenant` PostgreSQL schema, following
[C02](../../contracts/identity-clinic-access.md). A07 adds the clinic model,
service-local migrations and focused persistence checks. A08 implements clinic
creation, authorised profile edits, public profiles and booking eligibility.
A09 adds platform review, commission settings and durable audit events.
See [API setup and integration boundaries](docs/api.md).

A10 provides an identity-service-only clinic lookup for live staff membership
administration. Staff roles and memberships stay in identity; see
[staff integration](../identity/docs/staff-integration.md).

## Schema

One table, `tenant.clinics`, stores the C02 resource:

- UUID `tenant_id`, unique case-sensitive `slug`, nonblank `name`.
- `status`: `pending_review` (default), `active`, `rejected`, or `suspended`.
- Branding columns: `primary_color` (`#RRGGBB`), nullable HTTPS `logo_url`, and
  required plain-text `description` (may be empty).
- `consultation_price_minor`: nonnegative integer up to C01's safe JSON integer
  limit; `currency` is SGD. `commission_bps` is 0-10000, default 0.
- Nullable `review_reason` and UTC `created_at`/`updated_at`.
- A08 adds external `creator_subject_id` and `membership_provisioned` (default
  false). The latter is set only after identity confirms the creator membership.
  Existing A07 rows remain unprovisioned until deliberately reconciled.

Ordinary columns keep the schema small; the API maps branding and price to the
contract's nested JSON objects. A database trigger rejects slug changes,
preserves creation time and advances update time for ORM and SQL writes.
Indexes support active profiles ordered by name/ID and status-filtered admin
profiles ordered by creation/ID. UUIDs are generated by the ORM; operator SQL
inserts supply an explicit UUID.

There are no cross-service foreign keys or writes. Activation defaults to
pending review. A08 keeps a clinic non-bookable until identity membership
provisioning and approval succeed. Scheduling must call the booking-profile
gate before accepting new slots/holds/bookings when S02/S03 are implemented.
A09 enforces legal review transitions, reason requirements and audit events.
The API enforces those workflows; database constraints protect stored values.
The HTTPS check is a storage guard; the API validates URLs and plain-text
input and omits commission/review details from public profiles.

`tenant.audit_events` records administrative changes with actor subject ID,
clinic ID, action, previous/new values, review reason and UTC occurrence time.
The actor is an external identity ID, without a cross-service foreign key.
Audit rows and clinic changes commit atomically. Ordinary UPDATE/DELETE is
rejected by a trigger; clinic deletion is restricted while audit rows refer to it.
These are local audit records; no EventBridge publication is included in A09.

## Fresh local setup (PowerShell)

From `services/tenant`, using Python 3.10+ and Docker Desktop:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
.venv\Scripts\python.exe -m pip install --no-deps --no-build-isolation -e ../../packages/python_common
.venv\Scripts\python.exe -m pip install --no-deps --no-build-isolation -e .
docker run --name telelink-a07-postgres -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=a07-local-admin -e POSTGRES_DB=telelink -p 127.0.0.1:55409:5432 -d postgres:17
docker exec telelink-a07-postgres pg_isready -U postgres -d telelink
```

Wait for `accepting connections`. Use `docker start telelink-a07-postgres` when
reusing this dedicated container. Provision once on a fresh disposable database:

```powershell
Get-Content -Raw scripts/create-local-schema.sql | docker exec -i telelink-a07-postgres psql -v ON_ERROR_STOP=1 -U postgres -d telelink
$env:SERVICE_DATABASE_URL = 'postgresql+psycopg://tenant:local-demo-only@127.0.0.1:55409/telelink'
.venv\Scripts\python.exe -m alembic upgrade head
.venv\Scripts\python.exe -m alembic current
.venv\Scripts\python.exe -m alembic check
```

The tenant role owns only its schema; provisioning fails if the role/schema
already exists. Tables and the Alembic version table stay in `tenant`.
Migration reflection includes only this schema; connections use the shared
PostgreSQL engine's `search_path=public` and UTC settings. Export the database
URL explicitly; Alembic does not load `.env`. Repeat upgrades are safe.
Downgrade with `alembic downgrade base` drops clinic data and its trigger function.

No root Compose changes are needed for this service-local task. Deployment should
provide managed credentials/TLS, separate runtime/migration grants and controlled
migration execution, following [F04](../template/docs/database.md).

## Focused verification

Tests require a **disposable database**: they downgrade and recreate tenant tables.

```powershell
$env:TEST_DATABASE_URL = $env:SERVICE_DATABASE_URL
$env:TENANT_TEST_ALLOW_RESET = '1'
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m pip check
Remove-Item Env:TEST_DATABASE_URL
Remove-Item Env:TENANT_TEST_ALLOW_RESET
docker stop telelink-a07-postgres
```

Without `TEST_DATABASE_URL`, PostgreSQL tests skip explicitly. CI provisions
PostgreSQL 17 and runs the suite. Checks cover fresh/repeated upgrades,
Alembic metadata parity, defaults, branding updates, UTC timestamps, invalid
fields, required fields in SQL, immutable/unique slugs, rollback and
downgrade/re-upgrade. Local verification also checks isolation from unrelated
public and identity tables and denial of cross-service writes.

A08 adds signed-token API checks, cross-clinic/revoked-role denial, strict writable
fields, pagination and lost/mismatched provisioning acknowledgements. Local
verification also used an actual Floci PKCE token/JWKS and separate HTTP tenant
and identity servers: creation recovered after a provisioning failure and tenant
restart, then profile editing, active/suspended booking checks and membership
revocation passed. That A08 check used operator SQL for review transitions.

A09 verification passed all review transitions, strict commission/reason inputs,
concurrent retries, append-only audit checks and rollback on audit insertion
failure. Real Floci patient/platform PKCE tokens and separate HTTP services also
passed platform-only listing, approval/suspension/reactivation, commission changes,
public/booking eligibility, persisted audit events and immediate denial after
platform-role removal. Actual scheduling integration remains future work.
