## Purpose and success criteria

Create the persistence foundation needed by the later billing checkout, webhook
and payment-read tasks. B01 owns charges, opaque provider references and immutable
commission snapshots. A successful result is a small SQLAlchemy model and Alembic
migration that work under a restricted PostgreSQL role, preserve historical amounts
and pass focused persistence and migration checks.

The requirements come from `implementation-plan.md`, `plan.md`, C01
(`contracts/api-conventions.md`), C03 (`contracts/booking-payment.md`) and C04
(`contracts/prescription-order-quote.md`). F04, C03 and C04 are merged. Preserve
these contracts and the independent service boundaries.

## Selected approach

Use one `billing.payments` table for both payment purposes and their historical
attempts. Follow the existing document and fulfilment service conventions for
SQLAlchemy 2, psycopg 3, UTC connections, restricted provisioning and service-local
Alembic history. Use the shared technical database helper rather than introduce
another connection abstraction.

A separate ledger and provider-attempt subsystem would add accounting and
settlement concepts beyond this task. They are not needed to store C03 payments
and their trusted financial snapshots.

## Data model

Application IDs are UUIDs. External provider references remain opaque text.

| Column | Storage and meaning |
| --- | --- |
| `payment_id` | UUID primary key, generated by the application |
| `tenant_id`, `patient_id` | Required external UUID references |
| `purpose` | Required `consultation` or `medication_delivery` |
| `appointment_id` | Required for consultation, otherwise null |
| `order_id`, `quote_id` | Both required for medication/delivery, otherwise null |
| `status` | Required C03 payment state; default `pending` |
| `resolution` | Required `none` or `refund_required`; default `none` |
| `amount_minor` | Required total charge in integer minor units |
| `currency` | Required `SGD` |
| `commissionable_minor` | Required consultation amount or medication subtotal |
| `delivery_fee_minor` | Required fee, zero for consultation |
| `commission_bps` | Required integer basis-point snapshot |
| `commission_amount_minor` | Required integer platform commission snapshot |
| `clinic_amount_minor` | Required integer gross non-platform amount snapshot |
| `provider` | Required nonblank provider namespace; supplied explicitly |
| `provider_account_id` | Optional nonblank provider account namespace |
| `provider_checkout_id` | Optional nonblank provider checkout reference |
| `provider_payment_id` | Optional nonblank provider payment reference |
| `provider_idempotency_key` | Optional nonblank persisted provider checkout-operation key |
| `created_at`, `updated_at` | Required timezone-aware database timestamps |

The permitted states are `pending`, `succeeded`, `failed`, `refund_pending`,
`refunded` and `refund_failed`. These model provider outcomes and refunds;
`refund_required` remains an operational resolution, not a payment status.
`refund_required` is permitted only for `succeeded`, `refund_pending` and
`refund_failed`. A `refunded` payment must have resolution `none`.

Do not store patient clinical content, delivery addresses, card details, provider
secrets or raw webhook payloads in this table. No public response serializer or
payment endpoint is introduced by B01.

## Database invariants

### Resource links and money

- Enforce the exact purpose/link combinations in the table above with a database
  check constraint. There are no foreign keys to another service's tables.
- Every monetary column is a nonnegative PostgreSQL bigint no greater than
  `9007199254740991`, C01's safe JSON integer limit. Currency is `SGD`.
- `amount_minor = commissionable_minor + delivery_fee_minor`.
- Consultation has `delivery_fee_minor = 0` and
  `commissionable_minor = amount_minor`.
- `commission_bps` is between 0 and 10000 inclusive.
- `commission_amount_minor = floor(commissionable_minor * commission_bps / 10000)`.
  Cast the multiplication to PostgreSQL numeric before multiplying, so valid
  large integer inputs cannot overflow bigint during validation.
- `clinic_amount_minor = amount_minor - commission_amount_minor`.
- Delivery fees do not attract commission. The clinic amount is the gross
  non-platform portion, including delivery fees; it does not assert a Stripe net
  payout or provider settlement result. X03 and later billing tasks own those
  provider decisions.

Example: a medication subtotal of 2000, delivery fee of 500 and commission rate
of 1000 basis points produce total 2500, commission 200 and clinic amount 2300.
Integer rounding must also work for zero amounts, zero/full commission and
fractional-minor-unit commission results.

### Immutable snapshots and timestamps

Use a schema-local PostgreSQL update trigger to reject changes to the payment ID,
tenant/patient, purpose/resource links, currency and all financial snapshot
columns after insertion. This also protects direct SQL writes. Price or clinic
rate changes cannot rewrite a historical payment.

Preserve the original `created_at` on updates and refresh `updated_at` using the
database clock, following existing service patterns. ORM metadata must fetch
database-generated timestamps correctly. Mutable status, resolution and provider
references remain available for later provider processing.

State names and valid resolution combinations are enforced here. Authentication,
verified provider authority and legal transition handlers belong to the later
billing API/webhook tasks; schema validation does not establish payment truth.

### Provider references and lookup indexes

Provider checkout IDs, payment IDs and operation keys are individually unique
within their provider/account namespace when present. Treat a null account as
the same platform-account namespace for uniqueness, while allowing any number
of rows with an unset reference. Use PostgreSQL 17's null-equality support on
partial unique indexes to express this without fabricated account IDs.

Add scoped lookup indexes for patient and clinic payment lists ordered by
`created_at, payment_id`, and lookup indexes for appointment/order history.

Do not make appointment/order references unique across all payment rows: failed
attempt retries and real duplicate-charge history must remain representable.
In particular, a late success for a previously failed attempt must be storable
alongside another success and flagged for refund review. The one-current-checkout
policy requires transactional checkout coordination in B02/B06; B01 does not
claim to implement checkout concurrency or that integration.

## Files and service boundaries

Place the model, database helper, Alembic configuration/revision, Python package
configuration, dependency lockfile, sanitized environment example, provisioning
scripts, persistence tests and README under `services/billing/`.

Add a dedicated `.github/workflows/billing-checks.yml` using the repository's
existing PostgreSQL 17 / Python 3.10 / Ruff / pytest conventions. This is a new
service-specific workflow, not a change to existing service checks.

Provision a restricted `billing` database role and `billing` schema once, before
running migrations as that role. Store `alembic_version` in `billing`; restrict
Alembic reflection to that schema. Downgrade removes only objects created by
the billing migration and preserves its provisioned schema and other services.

Use explicit environment configuration for Alembic, including
`SERVICE_DATABASE_URL`. Document that a sanitized `.env.example` is a reference
and Alembic does not automatically load it. Never run migrations at application
startup or use the provisioning administrator as the service role.

No root Compose, frontend routes, shared API/event contracts or other services'
implementation files change. Existing draft PR #138 remains the implementation
PR for this task.

## Verification and local data protection

Use a separate disposable PostgreSQL 17 container for B01 checks. Do not use the
developer's persistent clinic database on port 55411 or reset Compose volumes.
Persistence tests require both `TEST_DATABASE_URL` and
`BILLING_TEST_ALLOW_RESET=1`, since they exercise downgrade and delete billing
test data. Fail on missing reset consent when a test URL is supplied; report
persistence tests as skipped if no test database was supplied.

Verify:

1. Fresh upgrade, repeated upgrade, Alembic model/schema parity, downgrade and
   re-upgrade work under the restricted billing role.
2. An unrelated schema/table sentinel, its contents and public-schema objects
   survive every migration operation; billing cannot modify the sentinel.
3. Both payment purposes persist with UUIDs, UTC timestamps and valid snapshots.
4. Invalid links, statuses, resolution combinations, currencies, amounts,
   commission rates and calculations fail at the database boundary.
5. Snapshot and ownership mutations fail through ORM and direct SQL; legitimate
   status/provider updates preserve creation time and refresh update time.
6. Provider uniqueness respects provider/account namespaces, including null
   account values, while unset references and historical attempts remain valid.
7. Zero/boundary amounts and commission rounding work without bigint overflow.
8. Ruff lint/format checks, relevant pytest checks and dependency consistency pass.

Add focused regression tests before the corresponding model/migration code and
confirm their initial failure. Record actual commands and observed results in
the README and PR. CI must run PostgreSQL checks rather than silently skip them.
